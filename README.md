
# Платформа аналитики и прогнозирования тарифов грузоперевозок (Smart Logistics)

Проект реализует сквозной пайплайн данных от сырых данных до ML-модели и пакетного скоринга, разворачиваемый одной командой.

## Архитектура и стек
- **СУБД:** PostgreSQL 17 (используется для всех слоев: Raw, Core, Mart).
- **ETL (Вопрос 1):** Python 3.11 + `psycopg3`. Логика очистки вынесена в SQL для максимальной производительности, оркестрация (управление транзакциями, идемпотентность, логирование) — на Python.
- **Аналитический слой (Вопрос 2):** SQL (материализованные представления, оконные функции, CTE).
- **ML (Вопрос 3):** Python, `CatBoost`, `scikit-learn`, `pandas`. Валидация по времени (Time-Based Split).
- **Инфраструктура:** Docker Compose (поднимает БД, инициализирует данные, запускает ETL и ML).


## Инструкция по запуску
На чистой машине с установленным Docker и Docker Compose выполните в корне проекта - `docker compose up --build`  

* Контейнер postgres развернет базу данных.

* Контейнер init создаст схемы, выполнит schema.sql, synthetic.sql и все миграции.

* Контейнер etl загрузит и очистит данные (завершится с кодом 0).

* Контейнер ml обучит модель и сохранит прогнозы (завершится с кодом 0).

Контейнер с базой данных останется работать в фоне. Для остановки нажмите `Ctrl+C` и выполните `docker compose down`.



## 1. ETL и Data Quality
Пайплайн параметризован окном дат и является строго идемпотентным (используется `DELETE` по партиции `loading_date` + `INSERT` внутри одной транзакции).

* **Очистка:** Отфильтровываются строки с `price <= 0`, для RUB — `price <= 1000`, `distance <= 0`, отрицательным весом/объемом и неизвестными городами.

* **Карантин:** Все отбракованные строки не теряются, а сохраняются в `core.dq_quarantine_prices` с указанием `reason_code` и снимком полей (`payload JSONB`).

* **Валюты:** Конвертация в RUB происходит строго по курсу на `nearest_rate_date`. Если курса нет — строка отправляется в карантин (fallback на `loading_date` запрещен).

* **Категории:** `weight_category` и `volume_category` пересчитываются на лету по жестким бизнес-правилам с округлением.

* **Ограничение исходных данных:** Сделки за последний день снимка (`2026-10-26`) еще не прошли ночной джоб разметки аномалий, поэтому у них `outlier_mark = false` по умолчанию. ETL сохраняет флаг «как есть» и не пересчитывает его. Фильтрация выбросов происходит на этапе витрин и ML.

## 2. DWH и аналитические витрины
Слой `mart` состоит из дедуплицированного справочника городов (`dim_cities_dedup`), унифицированного справочника кузова (`dim_body_group`) и материализованного представления `mart_route_card`.

Ключевые инженерные решения:

* **Дедупликация городов:** В источнике `gc_id` не уникален (Москва, Казань). Оставляем запись с `MIN(id)`, чтобы `JOIN` не размножал сделки.

* **Fallback кузова (3 уровня):** Сначала берем данные из `price_body_types`, если там пусто — из `prices.body_type`, если и там пусто — ставим `'Не указан'`. Это спасает `~2%` записей от потери.

* **Защита от fan-out:** Так как у одной сделки может быть несколько кузовов одной группы, используется `SELECT DISTINCT (price_id, body_group)`.

* **price_dates как источник месяцев:** Долгосрочная заявка дает статистику на весь срок своего действия (`loading_date` — `end_loading_date`).

* **MoM/YoY:** Рассчитываются через `LAG` с жесткой проверкой, что предыдущий месяц является календарно соседним. Никаких «последних доступных» данных.

* **reliability_level:** HIGH требует `trips_count >= 30`, `carriers_count >= 5` и свежести последнего месяца `≤ 30` дней от `as_of = 2026-10-26`. Для исторических месяцев HIGH недостижим по определению (сентябрь 2026 — 26 дней, октябрь 2026 — 0 дней).

`prices.body_type` — это `id_from_1C`. В `synthetic.sql` значения `id` и `id_from_1C` совпадают, поэтому тестовая реализация использует упрощённый `JOIN`.  
В `production` необходимо `JOIN` через `body_types.id_from_1C`:


```
left join body_types bt 
  on bt.id_from_1C = p.body_type
left join mart.dim_body_group bg_bt 
  on bg_bt.body_type_id = bt.id
```


## 3. ML Feature Engineering & Batch Inference
**Методология**  
* **Защита от утечек (Data Leakage):** Исключены `price_with_vat`, `price` / `distance`, `price_group_stats.*` и `price_group_id`.

* **Time-Based Split:** Train (2026-07-26 — 2026-10-05), Test (2026-10-05 — 2026-10-26), Future (> 2026-10-26). Случайного перемешивания нет.

* **Фичи:** Расстояние, регионы и координаты (раздельно для отправления и назначения), вес/объем, тип кузова, sin/cos кодирование дня года, месяца и дня недели.

**Результаты на тестовой выборке**  

| Модель | R² | MAPE | RMSE | MAE |
| :--- | :--- | :--- | :--- | :--- |
| **CatBoost (основная)** | **0.9194** | **15.63%** | **54 449 ₽** | **27 996 ₽** |
| Ridge (бейзлайн) | 0.8421 | 49.41% | 76 183 ₽ | 47 786 ₽ |

**Примечание:** Метрики полностью совпадают с ориентирами из `ml-report.md`. Отсутствие аномально низкого `MAPE (< 5%)` доказывает отсутствие утечек данных.

**Обработка аномалий в тесте:** В тестовой выборке присутствуют «неразмеченные выбросы» из генератора (`outlier_mark = false`, но цена искусственно умножена на `0.25` или `4.0`). Модель прогнозирует справедливую рыночную цену, из-за чего на таких сделках `APE > 400%`. Это не ошибка пайплайна — модель корректно игнорирует «битые» значения, которые не попали в карантин DQ.

Результаты скоринга сохраняются в `mart.ml_price_predictions` для аналитики «Факт vs Прогноз».



## Примеры SQL для проверки  

**1. Проверка журнала ETL:**  
```
select run_id,   
       status,   
       rows_read,   
       rows_loaded,   
       rows_quarantined   
  from core.etl_run_log   
 order by run_id desc 
 limit 3;
   ```  

**2. Причины попадания в карантин:** 

```
select reason_code, 
       count(*) 
  from core.dq_quarantine_prices 
 group by 1 
 order by 2 desc;
```

**3. Проверка рыночного коридора (Москва -> Казань, Тент, FTL):**  

```
select month, 
       trips_count, 
       carriers_count, 
       p25_trip, 
       median_trip, 
       p75_trip, 
       cv_rate, 
       reliability_level
  from mart.mart_route_card
 where loading_city_gcid = 1001 
   and unloading_city_gcid = 1003
   and body_group = 'Тент' AND weight_category = 'FTL'
 order by month desc 
 limit 5;
```

**4. Сравнение Факт vs Прогноз (Топ-5 ошибок ML):**  

```
select price_id, 
       loading_date, 
       body_group, 
       actual_price_rub, 
       predicted_price_rub, 
       round(ape_pct::numeric, 2) as error_pct
  from mart.ml_price_predictions
 where actual_price_rub is not null
 order by ape_pct desc 
 limit 5;
```
